## А. Первые 10 минут в новом чате

**Главное правило:** проект ведётся по разделу **О** — тот же порядок, те же команды, те же проверки.
Остальные разделы — справочник.

Песочница между сессиями теряет pip/apt-пакеты, `.git/config` и иногда `.git/refs/`. Поэтому всегда по порядку:

```bash
cd /home/user
# 1. Синхронизация с GitHub (GitHub — источник истины, воркплейс может отставать)
mkdir -p .git/refs/heads .git/refs/tags
ls .git/config 2>/dev/null || printf '[core]\n\trepositoryformatversion = 0\n\tfilemode = true\n\tbare = false\n\tlogallrefupdates = true\n[remote "origin"]\n\turl = https://github.com/AgentSharik/WAD.git\n\tfetch = +refs/heads/*:refs/remotes/origin/*\n[branch "main"]\n\tremote = origin\n\tmerge = refs/heads/main\n' > .git/config
git fetch -q origin main && git rev-parse HEAD FETCH_HEAD     # должны совпасть; если HEAD отстал и своих правок нет → git reset --hard FETCH_HEAD
git status -sb
```

```bash
# 2. Инструменты проверки (в песочнице НЕ сохраняются между сессиями, ставятся заново)
curl -sL -o /tmp/ps.tar.gz https://github.com/PowerShell/PowerShell/releases/download/v7.4.6/powershell-7.4.6-linux-x64.tar.gz
mkdir -p ~/.cache/ps && tar -xzf /tmp/ps.tar.gz -C ~/.cache/ps && chmod +x ~/.cache/ps/pwsh
~/.cache/ps/pwsh -NoProfile -Command "Install-Module PSScriptAnalyzer -Scope CurrentUser -Force -AllowClobber"
```

```bash
# 3. Убедиться, что репозиторий живой
~/.cache/ps/pwsh -NoProfile -Command "Get-ChildItem -Recurse -Filter *.ps1 | ForEach-Object { \$t=\$null; \$e=\$null; [void][System.Management.Automation.Language.Parser]::ParseFile(\$_.FullName,[ref]\$t,[ref]\$e); if (\$e.Count) { Write-Host \$_.Name; \$e } }; Write-Host 'разбор завершён'"
python3 extras/audit/tools/url_check.py 2>/dev/null | head        # живость внешних ссылок (нужен curl)
```

Затем прочитать: верхний блок `CHANGELOG.md`, раздел **Е** (дефекты) и раздел **З** (что проверено) этого файла.

Токен GitHub (fine-grained, **Contents + Workflows** на репозиторий) спрашивать у автора в начале чата, если нужен push.
Токен передавать **только в URL команды push**; в `.git/config` не сохранять; в выводе маскировать.

## Б. Что это за проект и как о нём говорить

**WAD (Windows Auto-Deployment)** — автоматическая установка и пост-установка Windows для домашних ПК.
Один запуск — готовая система. Два сценария с одинаковым результатом: **Clean** (Windows уже стоит, вход — `loader.ps1`)
и **Custom** (чистая установка, вход — `autounattend.xml`).

Правила речи (требования автора, не обсуждаются):

- Тема **офисного пакета закрыта**: не обсуждать, не менять, не поднимать в доках, коммитах и сводках.
- Проект — «мой/наш». Продукт везде называется **WAD**; старые названия («Менеджер автоматической настройки»,
  «Загрузчик») — только как исторические в CHANGELOG.
- Весь текст — код, комментарии, CHANGELOG, README, коммиты, сводки — **по-русски**.
- Автор — не сетевой эксперт: объяснять без жаргона, на его же коде.
- В примерах и доках — только вымышленные данные (`PC`, `Admin`, `C:\Windows\Setup\Scripts`).
- Интерфейс не должен врать: если что-то не проверено — писать «не проверено», а не предполагать.
- **Палитра интерфейса:** в README название палитры **не упоминается** (решение автора 2026-09-11: читателю это ничего
  не говорит). Описываем словами: тёмное окно, спокойные сине-серые тона, контраст текста не ниже 7:1. Точные значения
  цветов — в разделе Д; в код без нужды не лезть.

## Д. Зафиксированные решения (не менять без причины)

1. **Два режима, а не один набор.** В Custom часть работы делает файл ответов — поэтому 4 задачи и 18 пакетов
   в списке очистки, в Clean — 5 задач и 33 пакета. Разница вычислена, а не забыта. Убирать нужно не режимы,
   а физические копии файлов (4 файла идентичны байт-в-байт).
2. **Разметка диска только вручную.** Автоматизация исключена осознанно: риск форматирования раздела с данными
   выше выгоды.
3. **Хэши для обновляемых ссылок не фиксируются.** Chrome Enterprise MSI и подобные файлы вендор перезаливает
   (проверено по заголовкам: Chrome обновился в день проверки) — прибитый SHA256 сломает установку. Для стабильных
   файлов (ShareX, qBittorrent, WinRAR, K-Lite) хэш задать можно; для обновляемых правильнее проверять
   цифровую подпись (`Get-AuthenticodeSignature`).
4. **Пароль администратора в Custom — пустой и с автологином.** Необходимо для установки без участия человека;
   в README это записано в ограничениях честно.
5. **Логи — в «Документах» пользователя** (`Start-Transcript` внутри модулей). Для чужой машины лучше
   `C:\ProgramData` — это в плане v2.
6. **Палитра интерфейса** — тёмная, значения точные: `#1E1E2E` фон, `#181825` панели, `#89B4FA` акцент,
   `#A6E3A1/#F9E2AF/#F38BA8` статусы, текст `#CDD6F4`. Контраст всех пар выше 7:1.

## Е. Известные дефекты (проверено по коду, не на живой Windows)

1. ~~**Статусы задач не отражают реальность.**~~ **Исправлено 2026-09-11** на уровне модулей: каждый модуль
   перехватывает свои предупреждения, печатает итог со списком проблем и отдаёт код 1 (`Show-FailureVerdict`,
   подмена `Write-Warning` в области скрипта), проверка «не админ» тоже отдаёт 1. Проверено пробой механизма
   в песочнице (предупреждение → 1, чисто → 0), на живой Windows — нет. Осталось на v2: подробный отчёт
   по шагам (`result.json`) и продолжение работы после сбоя.
2. **Лог менеджера не пишется в файл** — строки уходят в скрытую консоль.
3. **Крестик при закрытии показывает «СИСТЕМА НАСТРОЕНА»** даже в середине установки; дочерние процессы продолжают работу.
4. **Ветка «нет интернета» в `loader.ps1`** советует запустить `Loader.cmd`, который никто не создаёт.
5. **ShareX:** фиксированная пауза 30 секунд вместо ожидания установщика и завершение процесса по имени
   `ShareX-20.2.0-setup-x64` при установке версии 21.0.0.
6. ~~**Кнопка «GITHUB РАЗРАБОТЧИКА»** в менеджере режима Custom ведёт на чужой репозиторий.~~ **Исправлено 2026-09-11:** ведёт на `AgentSharik/WAD`.
7. **`Custom/clean-and-photo.ps1` — единственный файл без BOM.** Исправлено 2026-09-11: CI под Windows PowerShell 5.1 показал, что дело не косметическое — файл не разбирается вовсе (строка 91, `Unexpected token`), то есть на домашнем ПК без PowerShell 7 скрипт не выполнился бы. Урок: проверка синтаксиса в CI идёт под 5.1 и ловит кодировку, локальный pwsh 7 — нет (он читает UTF-8 без BOM корректно).
8. **`reset-setup-scripts.ps1` удаляет папку `C:\Windows\Setup\Scripts` целиком** — на чистой Windows безопасно,
   в OEM-образах может задеть чужие файлы.
9. **Логика загрузки продублирована трижды:** `loader.ps1`, скрипт внутри XML и копии модулей в двух каталогах.
10. **Таск `PauseWindowsUpdate`** в режиме Custom регистрируется от `LocalService` в ветку `HKLM\…\WindowsUpdate\UX\Settings`
    (в Clean — от `SYSTEM`). Вероятно, не срабатывает — проверить в ВМ.
11. **`loader.ps1` не сообщает об ошибке**, если папки со скриптами нет: проверка `Test-Path` без ветки `else` —
    окно просто закроется. Учитывать при переименовании структуры (раздел Л плана v2).

## Ж. Куда что класть и как добавлять

- **Новый модуль** → `Scripts/` в оба режима (пока структура не сведена) + строка в `$ScriptsToRun` в обоих менеджерах.
- **Новая задача для режима Custom** → учесть, что часть работы уже сделал файл ответов: не дублировать.
- **Правка существующего скрипта** → патч-скриптом с проверкой якоря (`assert`), никогда «переписать файл целиком» (О.3).
- **Файлы скриптов:** имена латиницей, кодировка UTF-8 **с BOM**, переводы строк CRLF — как в репозитории.
- **Тексты и объяснения** — по-русски, без жаргона; в интерфейсе не врать (см. раздел Б).
- **Материалы аудита и разборы** → `extras/`, не в корень и не в README.

## И. Коммит, push, проверка (GitHub)

Коммит после **каждой** завершённой партии правок; сообщение по-русски.
Продуктовые партии — с версией: `0.4: что сделано`. Мета-партии (документы, структура, CI, без изменения
скриптов) — без версии: `оформление: что сделано`. Версия в CHANGELOG только за изменения продукта.

```bash
cd /home/user && find . -name __pycache__ -type d -not -path "./.git/*" -exec rm -rf {} + 2>/dev/null
git add -A && git -c user.name="AgentSharik" -c user.email="agentsharik@users.noreply.github.com" commit -q -m "0.3.1: что сделано, по-русски"
git push -q "https://x-access-token:${T}@github.com/AgentSharik/WAD.git" main
curl -s https://api.github.com/repos/AgentSharik/WAD/commits/main | grep -m1 '"sha"'   # сверить с git rev-parse HEAD
```

- Если push отклонён из-за файлов в `.github/workflows/` — у токена нет права **Workflows**: попросить автора.
- Массовое удаление (перезачистка папок, сведение копий) — тоже обычный коммит: производственные файлы не теряются,
  история сохраняется.
- Проверка бейджа: `curl -sI https://github.com/AgentSharik/WAD/actions/workflows/checks.yml/badge.svg | head -1`.

## К. Версии и релизы

1. Нумерация: `0.x` — до первых внешних пользователей, `1.0` — первый публичный релиз. Теги ставить на каждый релиз:
   `git tag -a v0.4 -m "…" && git push … main --tags`.
2. `CHANGELOG.md` — новый блок сверху: `## X.Y.Z — человеческое описание`, подразделы **✨ Новое / 🐞 Исправлено**.
   У исправлений писать причину: «раньше … → теперь …».
3. Порядок перед релизом: правки → проверки О.4 → CHANGELOG → тег → прогон в ВМ по протоколу О.6 → коммит и push → сводка автору.
4. Продуктовых файлов с версией пока нет (версия живёт в CHANGELOG и теге). Если появится константа версии —
   держать её в одном месте и обновлять вместе с тегом.

## Л. Тяжёлые файлы и история git

- В репозитории хранятся **только актуальные** тяжёлые файлы; старые — удалять вместе с историей.
- Перед добавлением чего-то больше мегабайта — спросить автора. Образы Windows, `.wim`, `.esd`, видео — в git не нужны.
- Если история уже засорена:

```bash
git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' | awk '$1=="blob" && $3>1000000' | sort -k3 -n -r | head
# чистка (после неё remote восстанавливать заново, push — принудительный):
pip install -q git-filter-repo
mkdir -p /tmp/keep && cp <актуальные файлы> /tmp/keep/
git filter-repo --force --invert-paths --path-glob '*.iso' --path-glob '*.wim'
git remote add origin https://github.com/AgentSharik/WAD.git
git push -q --force "https://x-access-token:${T}@github.com/AgentSharik/WAD.git" main
```

- В песочнице `.git/config` не сохраняется между сессиями — перед `filter-repo` создать его вручную (раздел А),
  иначе падает с `ValueError: dictionary update sequence element #0 has length 1`.

## Н. Технические грабли (наши, проверенные)

- **BOM и CRLF обязательны.** Без BOM в Windows PowerShell 5.1 кириллица превращается в кракозябры; при правках
  файлов из Linux не терять ни то, ни другое (проверка в CI).
- **Правки только патч-скриптом с якорем.** Крайние случаи: переносы `\r\n` и отступы — якорь брать ровно из файла,
  иначе `assert` не сработает (в июле правил `manager.ps1`: якоря с CRLF не совпадали, пока файл не прочитан в нужном режиме).
- **`-WindowStyle Hidden`** не поддерживается в PowerShell Core на Linux — тестовые запуски `Start-Process` в песочнице
  делаются без него.
- **`Start-Process -File` без `-Wait`** даёт гонку (ShareX ставится параллельно с K-Lite) — всегда `-Wait -PassThru`
  либо ожидание с таймаутом.
- **`Start-Transcript`** пишет управляющие последовательности цветов, если в скрипте есть `-ForegroundColor` — в логах
  модулей этого избегать.
- **WinForms-цикл** требует `Application::DoEvents()` при ожидании процесса, иначе интерфейс «зависает» и анимация стоит.
- **GUI в песочнице не проверить** — WinForms/GDI доступны только в Windows; любые выводы об интерфейсе делать по коду
  и по скриншотам автора.
- **`reg load`/`reg unload`** куста `C:\Users\Default\NTUSER.DAT` — только с паузой и сборкой мусора между операциями,
  иначе файл занят и куст не отмонтируется.
- **Имена файлов должны быть допустимы в Windows.** Двоеточие, звёздочка и подобные символы в имени файла
  ломают checkout на Windows-раннере CI: файлы вида `C:_Windows_Setup_Scripts_*.ps1` завалили первую сборку
  (2026-09-10). Проект под Windows — значит и имена должны быть Windows-совместимыми.
- **Копии расходятся.** 4 файла в двух каталогах идентичны байт-в-байт; править нужно оба, иначе появляется дрейф
  (уже есть: кнопка GitHub, BOM).
- **Репозиторий переименован `powershell-scripts` → `WAD` (2026-09-11).** Старые адреса GitHub отдаёт редиректом
  (проверено: `archive/refs/heads/main.zip` — 301→302→200), поэтому уже установленные копии лоадера качают архив дальше.
  Для `raw.githubusercontent.com` редирект **не проверялся** — в скриптах ссылаться только на `github.com/.../archive/...`.
  При любой правке ссылок менять их сразу в: `loader.ps1`, `autounattend.xml` (включая провенанс-комментарий в строке 3,
  где полезная нагрузка закодирована), оба `manager.ps1`, бейдж в README.

## О. Стандарт работы — регламент

### О.1. Старт сессии

Раздел А целиком: синхронизация, инструменты, проверка живости.

### О.2. Разбор запроса автора

1. Переписать запрос по пунктам (1, 2, 3…) в формулировках автора; итоговая сводка — по тем же номерам.
2. По каждому пункту **сначала посмотреть код**, потом решать: `grep -n`, чтение файла. Не чинить «по памяти».
3. Если пункт неоднозначен и цена ошибки высока — спросить автора **одним** сообщением со всеми вопросами сразу;
   мелкие развилки решать самому и упомянуть в итоге.
4. Согласованное правило: спорить можно и нужно, если есть факты; но решения автора (раздел Б, Д) не пересматривать.

### О.3. Как вносятся правки

- Только патч-скриптом, никогда «переписать файл целиком», никогда `sed` для многострочных фрагментов:

```python
p = 'Scripts/Scripts for Clean Windows/apps-install.ps1'
s = open(p, encoding='utf-8-sig', newline='').read().replace('\r\n', '\n')   # работаем в LF
a = '''точный старый фрагмент из файла'''
b = '''новый фрагмент'''
assert a in s, a[:80]          # обязательно: не найден якорь → код не тот, что вы думаете
open(p, 'w', encoding='utf-8-sig', newline='').write(s.replace(a, b, 1).replace('\n', '\r\n'))   # вернули CRLF и BOM
```

- После правки — прогон разбора синтаксиса и PSScriptAnalyzer (О.4), затем `grep` по изменённому месту.
- Дописывать в тот файл, где живут соседи по смыслу (карта — раздел Г).

### О.4. Как проверяется (на каждую партию правок)

```bash
~/.cache/ps/pwsh -NoProfile -File extras/audit/tools/check.ps1     # если появится; иначе командой из раздела А
```

- Разбор синтаксиса под PowerShell 7 (в песочнице) **и** в CI под 5.1 (у пользователя) — оба обязательны.
- PSScriptAnalyzer, уровни Error — падать на них.
- Для логики, которую можно вынести без Windows (разбор, состояние, отчёты, скачивание) — писать тесты и прогонять
  в песочнице, как это делалось при аудите: код достаётся **из репозитория целиком**, тест подключается к нему,
  а не к копии.
- Для Windows-части (реестр, установка, интерфейс) — протокол прогона в ВМ (О.6), «не проверено» писать честно.

### О.5. Проверка результата в песочнице

Отдельного «визуального смоука» нет: интерфейс и установка недоступны. Вместо него:

- сверка палитры/шрифтов/размеров по коду с исходным скриншотом;
- сверка текстов и подписей `grep`-ом (нет ли устаревших названий, «Cyberpunk», чужого репозитория в кнопке);
- сверка структуры и кодировок (BOM/CRLF) по всем файлам.

### О.6. Прогон в ВМ и релиз

1. Правки в `main` (или в ветке — по договорённости).
2. `CHANGELOG.md` — блок сверху с причиной каждого исправления.
3. Версия и тег (раздел К).
4. **Протокол прогона в ВМ — `extras/VM-PROTOCOL.md`** (составляет исполнитель, выполняет автор): снапшот до старта → установка/запуск →
   какие логи забрать (`Documents\*.log`) → отдельный прогон с отключённым интернетом → отдельный прогон со сбоем
   одного модуля → скриншот окна. **Релиз без прогона не выпускается.**
5. Коммит и push (раздел И), проверка SHA через GitHub API.
6. Сводка автору (О.8).

### О.7. План v2 (порядок не случайный: сначала честный результат, потом остальное)

| Этап | Что | Проверка |
|---|---|---|
| 1 | Общая библиотека: лог, скачивание, установка, результат шага, состояние, предполётные проверки | тесты логики в песочнице |
| 2 | Пилот: `apps-install.ps1` на новом скелете | прогон в ВМ |
| 3 | Остальные модули на общий скелет; сведение копий файлов | сравнение логов до/после |
| 4 | Менеджер: статусы из отчётов, продолжение после сбоя, отчёт на Рабочий стол | прогон с отключённой сетью |
| 5 | Загрузчик, CI, документация | зелёные проверки |
| 6 | `autounattend.xml`: шаблон и сборка, вшитые скрипты — файлами в репозитории | установка с нуля в ВМ |

Уже сделано вне плана (11 сентября 2026): честный код возврата в модулях и сверка копий в проверках —
это часть цели «честный результат», которая оказалась дешевле, чем казалось.

Детали плана — в `extras/PLAN-v2.md`.

### О.8. Итог автору

Одно сообщение по-русски: нумерация как в запросе; по каждому пункту — что сделано и **почему было так** (одна фраза
причины); отдельно — состояние репозитория (HEAD, что в CI); последней строкой — что осталось открытым.
Без английских вставок, без внутренней кухни инструментов.
