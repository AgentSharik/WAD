## 0.1. Уточнения после замечаний автора (10.09.2026)

Автор репозитория указал на три места в разборе. Два его замечания **подтвердились фактами**, и я их принимаю — ниже исправленные формулировки (пункты 6.1, 6.3 и 6.12 в теле отчёта обновлены):

1. **Про хэши — автор прав.** Я проверил заголовки: `googlechromestandaloneenterprise64.msi` имеет `Last-Modified: Thu, 10 Sep 2026 16:02:43 GMT` — то есть Google **перезаливает этот файл практически постоянно** (я проверял его же четырьмя часами позже). Прибитый SHA256 к такой ссылке означает «завтра установка сломается». Это не «отключённая проверка по недосмотру», а осознанное решение. Скорректировал: это больше не баг, а **упущенная возможность** — см. обновлённый п. 6.1 с правильным решением (Authenticode для rolling-ссылок + SHA256 там, где он стабилен).
2. **Про `reset-setup-scripts.ps1` — тоже автор прав.** На чистой Windows папки `C:\Windows\Setup\Scripts` действительно нет: её создаёт либо сам установщик ($OEM$), либо SetupComplete.cmd, либо — как здесь — скрипты проекта. Так что «снести всю папку» на чистой системе безопасно. Мой пункт 6.12 понижен до уровня «мелкое» и сужен до единственного реального случая: OEM/корпоративные образы, где в этой папке уже лежат чужие скрипты. Дополнительно проверил каскад в скрипте — он выстроен корректно: `schtasks /delete UnlockStartLayout` идёт **до** `rmdir`, поэтому «висящей» задачи с битым путём к `UnlockStartLayout.vbs` не остаётся.
3. **Про Office — «так и надо».** Принято как решение автора, спор не про код, а про риск. Технически всё работает: KMS-хост `kms.digiboy.ir:1688` доступен (проверил TCP-коннектом). Но пункт 6.3 я оставляю в отчёте в формулировке «риск, а не баг»: (а) активация Volume-редакции через публичный чужой KMS — это обход лицензирования, а не лицензия; (б) активация живёт ~180 дней и требует, чтобы чужой сервер был жив; (в) если проект будут использовать в организации, первым делом прилетит именно за это. Ничего «исправлять» не предлагаю — предлагаю в README одну строку-предупреждение, чтобы это был осознанный выбор пользователя, а не сюрприз.

**Итог правок:** из списка проблем пункт 6.1 понижен с 🔴 до 🟡, пункт 6.12 — до 🟡/мелкое, пункт 6.3 остаётся предупреждением. Общая оценка проекта — **6,5/10 → 7/10** (снял пункт за хэши, т.к. решение обоснованное).

```

│   ├── manager.ps1           385 строк  ← GUI-диспетчер
│   ├── initial-setup.ps1     215 строк  ← Edge, панель задач, Default User (только тут!)
│   ├── clean-and-photo.ps1   119 строк  ← Debloat, OneDrive, Фотографии, файл подкачки
│   ├── install-sys-components.ps1 139   ← VC++, DirectX, NetFx3, .NET 8
│   ├── apps-install.ps1      246 строк  ← Chrome, Steam, WinRAR, qBittorrent, ShareX, K-Lite
│   ├── office-install.ps1    177 строк  ← Office LTSC 2024 + KMS-активация
│   └── reset-setup-scripts.ps1 86 строк ← «режим камикадзе» — самоудаление
└── Scripts for Custom Windows (with Autounattend)/  (6 файлов, без initial-setup.ps1)
```

Важные наблюдения по структуре:

* **4 из 6 скриптов в двух папках байт-в-байт идентичны**, различаются только `clean-and-photo.ps1` и `manager.ps1`, а `initial-setup.ps1` есть лишь в «Clean»-версии — и это осознанное разделение на два режима (см. п. 6.6), а не случайная копипаста.
* **`autounattend.xml` — это результат работы генератора [schneegans.de/windows/unattend-generator](https://schneegans.de/windows/unattend-generator/)** (внутри лежит ссылка на конкретный коммит `cschneegans/unattend-generator@3b34a7d` и вся конфигурация в виде URL). То есть XML не написан руками, а собран из чек-боксов, и внутри него дополнительно лежат 14 системных скриптов (`RemovePackages.ps1`, `RemoveCapabilities.ps1`, `Specialize.ps1`, `DefaultUser.ps1`, `FirstLogon.ps1`, `UserOnce.ps1`, `unattend-01/02.ps1` и др.), которые распаковываются в `C:\Windows\Setup\Scripts`. Именно эти скрипты и делают «половину работы» до запуска менеджера в Custom-режиме.
* **Третья копия логики** — внутри `autounattend.xml`: скрипт `unattend-02.ps1` (223 строки) делает то же, что `loader.ps1` — качает с GitHub `main.zip`, кладёт в `C:\Windows\Setup\Scripts` и запускает `manager.ps1`. Разница только в папке: он берёт «Custom»-версию, а `loader.ps1` с GitHub — «Clean». Логику дублировать не обязательно — достаточно одного параметра режима.

## 6. Найденные проблемы (по убыванию важности)

### 🟡 6.1. «Проверка целостности»: механизм есть, но всегда выключен — и это осознанно
README: *«…по прямым ссылкам **с автоматической проверкой целостности**»*. В коде все 6 вызовов идут с `-ExpectedHash $null` (строки 113, 131, 158, 181, 202, 229), хотя сам механизм SHA256 **рабочий и проверен** (тесты 5.3: неверный хэш → выброс + удаление файла).

**Позиция автора (проверил — верная):** часть ссылок «вечнозелёные», и жёсткий хэш их сломает. Факты с заголовков:

| Ссылка | `Last-Modified` | Можно ли пиннить хэш |
|---|---|---|
| Chrome Enterprise MSI (`dl.google.com`) | **10.09.2026 16:02 GMT — т.е. обновляется постоянно** | ❌ нет, сломается |
| `aka.ms/vs/17/release/vc_redist.x64.exe` | обновляется с каждым сервисом VS 17 | ❌ нет |
| `cdn.akamai.steamstatic.com/…/SteamSetup.exe` | 20.05.2024 (редко, но без гарантий) | ⚠️ рискованно |
| `cdn.akamai.steamstatic.com`, ODT с `download.microsoft.com` | перезаливается вендором | ⚠️ рискованно |
| ShareX v21.0.0 (GitHub release) | ассет иммутабельный, **SHA256 опубликован вендором** | ✅ да |
| qBittorrent 5.2.3 (GitHub release) | ассет иммутабельный, хэш публикуется | ✅ да |
| WinRAR 7.23ru, K-Lite 1975 | в имени файла зашита версия, содержимое по этому пути не меняется | ✅ да |

**Что из этого следует (это уже не баг, а незакрытая возможность):**
1. Для GitHub-релизов и версионных файлов хэши **стабильны и публикуются вендором** — там пиннинг безопасен и ничего не сломает (ShareX, qBittorrent, WinRAR, K-Lite).
2. Для evergreen-ссылок (Chrome, `aka.ms/*`, Steam) правильный инструмент — не SHA256, а **проверка цифровой подписи** файла:
   ```powershell
   $sig = Get-AuthenticodeSignature $OutFile
   if ($sig.Status -ne 'Valid' -or $sig.SignerCertificate.Subject -notmatch 'Google LLC|Microsoft Corporation|Valve') {
       throw "Подозрительный источник/подпись: $($sig.Status)"
   }
   ```
   Это работает в Windows PowerShell 5.1 без внешних модулей, не зависит от версии файла и полностью решает исходную задачу автора («проверить, что скачалось то, что нужно, но не ломать установку при обновлении файла»).
3. Что стоит поправить минимально: **формулировку README**. Сейчас она обещает проверку целостности, которой нет ни в одном вызове — достаточно слова «с проверкой подписи/целостности там, где это возможно» или оговорки про обновляемые ссылки.

### 🔴 6.2. Ошибки глушатся → «зелёная галочка» врёт
`apps-install.ps1`, `install-sys-components.ps1`, `office-install.ps1`: каждый шаг обёрнут в `try/catch → Write-Warning`, а `exit` в конце не выставлен. Итог: скрипт возвращает 0 **всегда**. Менеджер лоялен к коду возврата, поэтому рисует «✓ Готово» даже при полном провале. Мой тест 5.4 воспроизвёл это один в один. Это главный архитектурный дефект: пользователь не может отличить реальный успех от тихого провала, а обещанная «отказоустойчивость» превращается в «тихое замалчивание».

### ⚠️ 6.3. Активация Office через чужой публичный KMS — это риск, а не баг
> **Позиция автора:** «виндовс офис, так и надо». Принято — оставляю пункт как осознанное предупреждение для пользователя, а не как ошибку кода. Ниже — только факты, которые стоит знать тому, кто этим скриптом пользуется.

`office-install.ps1:151–152` — `cscript ospp.vbs /sethst:kms.digiboy.ir` + `/act`. Это:
* **юридически** — обход лицензирования (Volume-ключ `FXYTK-…` + чужой KMS = пиратская схема активации, а не покупка);
* **безопасностно** — активация выполняется по незашифрованному KMS-протоколу на IP-адрес третьей стороны, которую вы не контролируете; сервер может исчезнуть, сменить владельца или отвечать чем угодно;
* **ненадёжно** — такая активация живёт 180 дней и требует постоянной связи;
* плюс отдельный «хак» рядом: `office-install.ps1:90` пишет в реестр `CountryCode = std::wstring|US` — типовой обход региональных ограничений.
Если проект позиционируется как «поставил и забыл для дома», этот шаг как минимум должен быть **опциональным, с явным предупреждением** и отдельно упомянут в README.

### 🟠 6.4. Безопасность ослаблена «из коробки» (ветка autounattend)
Во вшитых в XML скриптах (`Specialize.ps1`, `DefaultUser.ps1`, `UserOnce.ps1`) и настройках генератора:
* пустой пароль администратора + автологин (см. 5.8);
* `fDenyTSConnections=0` + правило брандмауэра RDP → **удалённый рабочий стол включён**;
* **SmartScreen выключен** (`SmartScreenEnabled=Off`, `DisableSmartScreen=true`), **Smart App Control выключен** (`VerifiedAndReputablePolicyState=0`), уведомления Defender/WTDS отключены и скрыт значок;
* машина переводится в `ExecutionPolicy RemoteSigned` + `AllowPowerShellScripts=true`;
* удаляется Windows Hello (в т.ч. вход по лицу).
Для игрового домашнего ПК это осознанный размен «удобство ↔ безопасность», но для ноутбука, который ходит в интернет, — плохая идея. Мини-патч: генерировать пароль или хотя бы убрать `PlainText`, а отключение защит сделать чек-боксом, а не дефолтом.

### 🟠 6.5. Загрузчик исполняет код с GitHub от админа без верификации
`loader.ps1` (и такой же вшитый `unattend-02.ps1`) качает `main.zip` и сразу запускает оттуда `manager.ps1` под админом с `-ExecutionPolicy Bypass`. Ни SHA256, ни проверки подписи, ни фиксации версии (тег/релиз). Любая компрометация аккаунта или подмена ветки = автоматическое выполнение произвольного кода с правами администратора на всех машинах, где запускали скрипт. Минимум, что стоит сделать: брать не `refs/heads/main`, а **тег релиза**, сверять SHA256 архива и, в идеале, подписывать скрипты Authenticode.

### 🟡 6.6. Два режима, а не «две копии»: логика подтверждена, риск — только в физических копиях

**Позиция автора (проверил — логика верная):** папки разделены не «на всякий случай», а потому что **до лоадера в двух сценариях делается разная работа**:

* **Custom** (установка ОС по `autounattend.xml`) — часть работы уже выполнил файл ответов: удалил пакеты, настроил систему, применил политики. Поэтому в Custom-менеджере **4 задачи, а `initial-setup.ps1` отсутствует** — повторять сделанное не нужно.
* **Clean** (чистая Windows, скачан один `loader.ps1`) — файла ответов не было, поэтому добавляется пятая задача `initial-setup.ps1`, воспроизводящая его работу, чтобы **на выходе в обоих сценариях получилась одинаковая система**.

Проверил это на данных. Разница между версиями `clean-and-photo.ps1` по списку удаляемых пакетов:

| Папка | Пакетов в списке |
|---|---|
| `Scripts for Clean Windows` | **33** |
| `Scripts for Custom Windows (with Autounattend)` | **18** |

«Лишние» 16 пакетов Clean-версии — Clipchamp, Bing Search, Office Hub, Sticky Notes, OneNote, Outlook, People, To Do, Wallet, DevHome, Камера, Карты, Диктофон, Microsoft Family, `windowscommunicationsapps` (и Copilot-провайдер) — **все до одного уже удаляются вшитым в XML `RemovePackages.ps1`**. То есть урезанный список Custom — не отставание, а расчёт: этих приложений в системе уже нет. Замысел «одинаковый результат обоими способами» подтверждается.

**Что остаётся реальной проблемой — не идея, а её реализация:**

1. **4 файла продублированы байт-в-байт** (`apps-install.ps1`, `install-sys-components.ps1`, `office-install.ps1`, `reset-setup-scripts.ps1`) — разница режимов их вообще не касается.
2. **Дрейф уже начался, и это доказуемо:**
   * в Custom-версии `manager.ps1:114` кнопка **GITHUB РАЗРАБОТЧИКА ведёт на `github.com/alexejnekrasov/powershell-scripts`** — в Clean-версии ссылка правильная. Правка легла только в одну копию;
   * Custom-версия `clean-and-photo.ps1` — **единственный файл без BOM**. При ручном запуске даст кракозябры; в штатном потоке маскируется перезаписью в UTF-8 с BOM внутри лоадеров.
3. **Любой будущий фикс надо делать дважды.** Пока правок мало и автор один — терпимо; с ростом числа правок дрейф станет нормой.

**Вывод (уточнённый):** архитектура двух режимов — правильная, её надо сохранить. Убирать нужно не папки, а **копии файлов**: два профиля запуска (какие модули идут + что уже сделано заранее), но один физический код.

### 🟡 6.7. Мёртвый код в «ветке без интернета»
`loader.ps1:84–89`: переменные `loaderPs1Path`/`loaderCmdPath` вычисляются, но файл `Loader.cmd` **никто не создаёт** — при этом сообщение пользователю гласит «запустите `Loader.cmd` с рабочего стола». Раньше это работало (видно в старой версии внутри `autounattend.xml`), при рефакторинге логику потеряли, а текст остался. Пользователь без интернета получит инструкцию к несуществующему файлу.

### 🟡 6.8. Логирование менеджера пишет «в никуда»
README: *«Прозрачное логирование: незаметная фоновая запись всех действий скриптов в отдельный лог-файл»*. В `manager.ps1` переменная `$LogDir` создаётся (стр. 46–47), но ни один файл не открывается: `Add-LogLine` — это обычный `Write-Output` в **скрытую** консоль. В итоге собственный лог менеджера теряется. Реальные логи появляются только из `Start-Transcript` внутри модулей (в «Документах»): `Initial_Setup.log`, `System_Optimization.log`, `System_Components_Install.log`, `software-install.log`, `office2024-install.log`, `windows-clean-scripts.log`. То есть логи есть, но «единого лога менеджера» — нет. Фикс — 2 строки.

### 🟡 6.9. Крестик закрытия показывает ложный «успех»
`manager.ps1:150–152` — закрытие окна в любой момент вызывает диалог **«СИСТЕМА НАСТРОЕНА… перезагрузите ПК»** (стр. 88). Если нажать ✕ в середине установки, пользователь увидит поздравление, а дочерние процессы продолжат работать в фоне (их никто не останавливает). Надо либо блокировать закрытие, либо честно писать «процесс прерван».

### 🟡 6.10. ShareX: гонка + устаревшее имя процесса
`apps-install.ps1:197–213`: установщик запускается **без `-Wait`**, ждём фиксированные 30 с (в тексте написано «20 секунд»), потом `Stop-Process -Name "ShareX-20.2.0-setup-x64"` — но ставится **21.0.0**, и процесс называется иначе → убийство не сработает. Если установка заняла больше 30 с, скрипт пойдёт ставить K-Lite параллельно. Лечится `-Wait -PassThru` + циклом ожидания с таймаутом.

### 🟡 6.11. Мелочи-несоответствия
* Нумерация шагов в `apps-install.ps1` пляшет: `[1/6]`, `[2/7]`, `[3/6]`… (стр. 108–224), шагов всего 6.
* Комментарий `# qBittorrent (Прямая ссылка на релиз 5.2.2 с libtorrent 1.2.x)` (стр. 174) при установке **5.2.3**, где libtorrent другой ветки.
* Возврат «Просмотра фотографий» (`clean-and-photo.ps1:97`) лишь **добавляет запись в `HKLM\…\Photo Viewer\Capabilities\FileAssociations`** — то есть приложение **появляется в списке «Открыть с помощью»**, но дефолтным не становится (на Win10/11 ассоциации защищены хэшем UserChoice). README обещает больше, чем делает скрипт.
* Файл подкачки трогается **только если ОЗУ < 32 ГБ** (стр. 106) — при большем объёме скрипт молча ничего не делает.
* В `autounattend.xml` вшитый `PauseWindowsUpdate.xml` регистрируется от **`S-1-5-19` (LocalService)** с `LeastPrivilege`, хотя тот же таск в `initial-setup.ps1` создаётся от **`S-1-5-18` (SYSTEM)** с `HighestAvailable`. Таск пишет в `HKLM\…\WindowsUpdate\UX\Settings`, куда у LocalService прав обычно нет → в «Способе 1» пауза обновлений, скорее всего, **молча не работает**. (Утверждать на 100% без живой Windows не могу, но несоответствие прав в двух версиях одного и того же таска — очевидный дефект.)
* `initial-setup.ps1` глушит службы обновления Edge (`edgeupdate`, `edgeupdatem`, `MicrosoftEdgeElevationService`) и чистит Active Setup. Edge остаётся в системе, но **перестаёт обновляться** — это потенциальная дыра безопасности; логичнее либо удалять Edge, либо не ломать его апдейтер.

### 🟡 6.12. `reset-setup-scripts.ps1` сносит всю папку (сужено после замечания автора)
Строка 61: `rmdir /s /q C:\Windows\Setup\Scripts`.

**Автор прав:** на чистой Windows этой папки **нет** — её создаёт либо сам установщик через `$OEM$`, либо `SetupComplete.cmd`, либо (в этом проекте) скрипты установки. Так что на чистой системе удалять нечего и «снести всю папку» — безопасный и осознанный выбор. Понижаю пункт до мелкого; остаётся ровно один узкий сценарий: **OEM- и корпоративные образы**, где в этой же папке уже лежат чужие `SetupComplete.cmd`/скрипты производителя — там «камикадзе» заденет и их. Если проект планируется для таких машин, надёжнее удалять по списку своих файлов.

Отдельно проверил каскад удаления — он **выстроен корректно**: `schtasks /delete /tn "UnlockStartLayout"` выполняется **до** `rmdir`, поэтому «висящей» задачи с битым путём к `UnlockStartLayout.vbs` не остаётся; `cd /d C:\` и `timeout /t 5` снимают проблему удаления папки, из которой запущен скрипт. Придирок по механике нет.

## 7. Безопасность и юридическая сторона (сводно)

| Что | Риск | Где |
|---|---|---|
| Запуск скачанного кода от админа без хэшей и подписи | Supply-chain: компрометация репо = выполнение кода у всех пользователей | `loader.ps1`, `unattend-02.ps1` |

Это не вирус, а скорее «перестраиватель системы под вкус автора» с несколькими спорными решениями.

## 8. Что сделано хорошо

* **Идея и UX.** Лоадер одним файлом → GUI с прогрессом и статусами по каждому шагу → самоочистка. Для домашнего сценария это удобно и красиво. GUI действительно рисуется кастомно (GDI+, градиентный блик, перетаскивание окна за любую точку), а не «из коробки».
* **Проработка «мелочей» установщика:** `-NoProfile`, `Set-StrictMode`, `$ProgressPreference='SilentlyContinue'`, TLS 1.2/1.3, подмена User-Agent, таймауты 300 с, ретраи с задержкой, fallback `WebClient`, отбраковка файлов <100 КБ, обработка кодов `3010` (нужна перезагрузка) и `1638` (уже установлено) — это уровень выше среднего любителя.
* **Все внешние ссылки живые** (проверено 24 шт.), версии софта, кроме K-Lite, актуальны на сегодня.
* **Код читаемый**: единый стиль, осмысленные комментарии на русском, разделение на этапы, логирование транскриптов в «Документы», корректная работа с кустом Default User (`reg load`/`reg unload` с проверкой в `finally`).
* **Честное отношение к данным пользователя:** разметка диска в «Способе 1» намеренно оставлена ручной — случайно снести раздел с личными файлами нельзя. Это правильное решение, редко встречающееся у авторов-автоматизаторов.

## 9. Итог

**Это не «мусорный репозиторий с 20 строками» и не вирус**, а живой, продуманный проект уровня «крепкий домашний автоматизатор»: ~1 500 строк читаемого PowerShell, красивый GUI, продуманная обработка ошибок на уровне отдельных установщиков, живые ссылки и аккуратная документация.

**Но:** «зелёные галочки» в интерфейсе ничего не гарантируют, проверка целостности в README заявлена — а в коде сознательно отключена (объяснение автора про «вечнозелёные» ссылки я проверил и принял: подпись вместо хэша закрыла бы вопрос), загрузчик исполняет неподписанный код из интернета от администратора, а активация Office сделана через чужой публичный KMS-сервер. Плюс ветка `autounattend` ощутимо ослабляет безопасность Windows (пустой пароль админа, включённый RDP, выключенный SmartScreen).

**Кому рекомендую:** домашнему пользователю, который понимает, что делает, готов один раз посмотреть логи в «Документах» и при необходимости доустановить пропущенное руками. Для рабочей/корпоративной машины, для малознакомых людей «поставь мне Windows» и для массового развёртывания — не рекомендую в текущем виде.

**Оценка: 7/10** (после разбора замечаний автора; первичная оценка была 6,5). Хорошая база, которой не хватает примерно десятка небольших правок, чтобы стать действительно надёжной.
