# v2: план перестройки проекта (без кода — только архитектура)

Составлено под сценарий: **домашние ПК, unattended, для сторонних людей, которые код не читают.**
Офисный модуль по твоей просьбе выведен из обсуждения и остаётся как есть — никаких комментариев по нему в этом документе.

---

## 1. Что не так сейчас (корневые причины, остальное — следствия)

1. **Файлы продублированы физически.** Две папки — это два обоснованных режима (см. уточнение в п.2), но 4 файла в них **идентичны байт-в-байт**, а два «разных» расходятся лишь частично. Плюс **третья копия** логики загрузчика живёт внутри `autounattend.xml`. Дрейф уже виден: в Custom-версии `manager.ps1` кнопка GitHub ведёт на чужой репозиторий, а Custom-версия `clean-and-photo.ps1` осталась без BOM.
2. **Связь модуль → менеджер построена на коде возврата.** Модуль глушит ошибки внутри (`try/catch` → `Write-Warning`) и всё равно выходит с 0 → менеджер рисует «✓ Готово». Менеджер физически не знает, что произошло внутри модуля.
3. **Нет состояния.** Установка — линейный прогон без памяти. Выключили ПК на середине — продолжения нет, а «режим камикадзе» уже мог удалить скрипты.

Отсюда всё остальное: логи пишутся в «Документы» текущего профиля, крестик показывает ложный успех, в ветке «нет интернета» советуют запустить несуществующий файл.

## 2. Целевая структура

> **Уточнение после объяснения автора.** Две папки — это два **режима**, и они обоснованы: в Custom-режиме часть работы делают скрипты файла ответов (`RemovePackages.ps1`, `Specialize.ps1`, `DefaultUser.ps1` и др.), поэтому там 4 задачи и урезанный список debloat; в Clean-режиме того же результата добивается `initial-setup.ps1` и полный список. **Режимы сохраняем как есть — убираем только физические копии файлов.**

```
repo/
├─ loader.ps1                    ← точка входа «для уже стоящей Windows» (режим Clean)
├─ autounattend.xml              ← установка с нуля (режим Custom), см. п.4
│
├─ src/
│  ├─ manager.ps1                ← UI + планировщик. Параметр -Mode Clean|Custom
│  ├─ modes.ps1                  ← два профиля: какие модули идут в каком режиме
│  │                               Clean  → 5 задач (с initial-setup)
│  │                               Custom → 4 задачи (initial-setup не нужен: сделал файл ответов)
│  │
│  ├─ lib/                       ← общее для всех модулей, один экземпляр вместо копий
│  │  ├─ Log.ps1                 ← единый лог: файл + консоль + уровень (INFO/WARN/FAIL)
│  │  ├─ Download.ps1            ← скачать / распаковать / проверить подпись или хэш
│  │  ├─ Install.ps1             ← exe/msi: коды 0/3010/1638, «уже установлено?», ожидание
│  │  ├─ Result.ps1              ← результат шага: Ok / Skipped / Failed + причина
│  │  ├─ State.ps1               ← состояние прогона + возобновление после сбоя
│  │  └─ Preflight.ps1           ← проверки перед стартом (см. п.5)
│  │
│  └─ modules/                   ← ровно один набор, без дублей
│     ├─ 10-initial-setup.ps1    ← запускается только в Clean-режиме
│     ├─ 20-clean-and-photo.ps1  ← внутри два списка: полный (Clean) и урезанный (Custom)
│     ├─ 30-sys-components.ps1
│     ├─ 40-apps-install.ps1
│     └─ 50-office.ps1           ← логика не меняется, только подключается к lib
│
└─ .github/workflows/ci.yml      ← авто-проверки на каждый пуш (см. п.7)
```

**Кто задаёт режим:** лоадер. `loader.ps1` с GitHub запускает `manager.ps1 -Mode Clean`; лоадер внутри `autounattend.xml` — `manager.ps1 -Mode Custom`. Пользователь ничего не выбирает и не может перепутать: режим определяется точкой входа, как и сейчас.

**Почему модули с числовыми префиксами:** порядок запуска читается глазами и задаётся именем файла, а не отдельным списком в трёх местах.

**Про `clean-and-photo.ps1`:** сейчас в Custom-версии список из 18 пакетов, потому что 16 уже удалил файл ответов. Вариант на проверку: держать **один полный список** и гонять его в обоих режимах — удаление уже отсутствующего пакета проходит молча (`-ErrorAction SilentlyContinue`), то есть в Custom это просто no-op. Если при тесте в VM окажется, что лишних ошибок в логе нет, — код модуля можно вообще не различать по режимам, и тогда от «двух версий» не останется даже параметра.

## 3. Три механизма, на которых держится v2

### 3.1. Результат вместо кода возврата

Каждый модуль в конце собирает отчёт и пишет его рядом в `result.json` (плюс возвращает объект):

```powershell
# внутри модуля — на каждый шаг
$Result = New-StepResult -Step 'Google Chrome' -Status 'Failed' -Detail 'HTTP 404'
$Result = New-StepResult -Step 'Steam'         -Status 'Skipped' -Detail 'уже установлен'
```

Менеджер после каждого модуля читает отчёт и красит статус по фактам:
`✓ Готово 6/6` · `⚠ Готово с ошибками (2/6)` · `✗ Сбой (модуль упал)` · `⚠ Нет отчёта`

Это ровно то, что делает ложные галочки невозможными: даже если модуль упадёт и вернёт 0 — менеджер увидит, что внутри было `Failed`.

### 3.2. Состояние и возобновление

```
C:\ProgramData\AutoSetup\state.json    ← какой модуль дошёл, что уже сделано, когда
C:\ProgramData\AutoSetup\logs\         ← логи вместо «Документов»
```

- Модуль отмечается пройденным **только** при `Failed = 0`.
- При старте менеджер смотрит `state.json` и, если прогон не завершён, продолжает с первого несделанного модуля.
- Если ПК выключили насмерть — RunOnce-запись поднимает менеджер при следующем входе (при условии `Failed = 0` до этого места, иначе честно спрашивает).
- Повторный запуск безопасен: всё, что уже стоит, модули определяют и помечают `Skipped`.

### 3.3. Уже установлено? (идемпотентность)

`Install.ps1` получает на вход признак установки — версию из реестра, наличие файла или имя пакета — и решает сам:
`не стоит → ставим` · `стоит старее → обновляем` · `стоит то же или новее → Skipped`.

Для чужой машины это ключевое: «поставил ещё раз» не должно ломать систему и тянуть 3 ГБ заново.

## 4. `autounattend.xml`

Сейчас это 1 100 строк, собранные генератором, с 14 вшитыми скриптами внутри, и в них — **дублирующаяся** логика загрузки (`unattend-02.ps1` качает репу так же, как `loader.ps1`).

Правильно:
- хранить XML как **шаблон + параметры** (язык, ключ, имя ПК, таймзона, аккаунт) и собирать его генератором, а не править руками;
- вшитые скрипты держать **в репозитории как файлы** (`src/unattend/…`), а в XML они попадают при сборке — тогда их видно, можно ревьюить и они попадают в CI;
- убрать дублирование загрузчика: внутри XML должен быть один вызов, который тянет релиз.

Это отдельный этап, его можно сделать после модулей.

## 5. Проверки перед стартом (Preflight)

Для чужого ПК в unattended-режиме это дешёвая страховка:

| Проверка | Зачем |
|---|---|
| Windows 10/11, разрядность | модули заточены под них |
| Свободное место (например, ≥ 20 ГБ) | иначе Office/игры посыпятся на середине |
| Интернет с ожиданием (до 5 минут) | частая причина «тихих» провалов |
| Уже запущен другой экземпляр | защита от двойного старта |
| Права администратора | иначе половина шагов молча не сделается |

Результат — «предполётный отчёт» в начале лога: сразу видно, запустится ли что-нибудь вообще.

## 6. Порядок работ (по этапам, каждый этап проверяем)

| Этап | Что делается | Как проверяем |
|---|---|---|
| 1 | `lib`: Log, Result, Download, Install, State, Preflight | тесты в песочнице: логика результатов, состояние, коды установщиков, скачивание |
| 2 | Пилот: `40-apps-install.ps1` на новом скелете | тесты + твой прогон в VM: должен честно показать 6/6 или список провалов |
| 3 | Остальные модули переводим на lib, сведение двух папок в одну | сравнение поведения до/после по логам |
| 4 | `manager.ps1`: статусы из отчётов, возобновление, отчёт на Рабочий стол | прогон в VM со специально отключённой сетью |
| 5 | `loader.ps1` + CI + документация (README, протокол тестирования) | CI зелёный, README читается человеком со стороны |
| 6 | `autounattend.xml`: шаблон + сборка, вшитые скрипты в репу | установка с нуля в VM |

Порядок не случайный: сначала «честный результат», потому что без него невозможно проверять остальное.

## 7. CI: робот вместо читателя

`.github/workflows/ci.yml`, раннер `windows-latest`:
- разбор синтаксиса **в Windows PowerShell 5.1** (не только в 7 — важно, ведь у пользователя 5.1);
- PSScriptAnalyzer на ошибки;
- проверка, что в каждом модуле есть запись отчёта;
- проверка BOM/CRLF — та самая мелочь, из-за которой кириллица превращается в кракозябры.

Красный CI = правку не смотрим. Это стоит 30 минут работы и навсегда убирает «а у меня не так отработало».

## 8. Зачистка текущего репозитория (решено: репозиторий оставляем)

Так как до релиза дело не дошло и все, у кого что-то было, — бета-тестеры, **совместимость не критична**. Но зачистка делается в два этапа, чтобы не смешивать «безопасное» и «ломающее».

### Этап A — безопасная уборка (старые лоадеры продолжают работать)

Порядок не случайный: сначала тег, потом уборка.

1. **Тег `v1.0-beta` на текущий `main`** — состояние беты становится неизменяемым ориентиром («вот что стояло у тестеров»). Ровно то, чего сейчас не хватает, когда надо понять, какая версия у человека на руках.
2. **Убрать 4 байт-в-байт дублика:** `apps-install.ps1`, `install-sys-components.ps1`, `office-install.ps1`, `reset-setup-scripts.ps1` — оставить по одному экземпляру.
3. **Влить в Clean-версию то, что есть только в Custom от 25 июля:** ассоциации фото через `dism /Import-DefaultAppAssociations` и ветку «ОЗУ ≥ 32 ГБ → отключить файл подкачки». Сейчас это самое свежее в репозитории и в «новую» папку оно не переехало.
4. **Починить кнопку GitHub** в Custom-версии `manager.ps1` (`alexejnekrasov` → `AgentSharik`).
5. **Добавить BOM** в Custom-версию `clean-and-photo.ps1` (единственный файл без BOM).
6. **README:** палитра называется Catppuccin Mocha, а не «Cyberpunk»; отметить, что скрин снят на Custom-версии (4 задачи по замыслу); добавить `CHANGELOG.md` — одна страница, где видно, что менялось и какого числа.

После этапа A система работает ровно как раньше, дублей нет, история сохранена.

### Этап B — переезд в `src/` по этой архитектуре

Здесь ломается совместимость, и это надо планировать, а не обнаружить. Конкретно:

* `loader.ps1:124` жёстко ищет `Scripts\Scripts for Clean Windows`, и у проверки **нет ветки `else`** — если папка исчезнет, ничего не произойдёт: не ошибка, а тишина, окно просто закроется. Самый неприятный вид поломки для человека, который «просто запустил и ушёл».
* Флешки, записанные раньше, везут свою копию логики внутри `autounattend.xml` и после переезда тоже не соберут новую версию.

Два варианта на выбор:

| | Что делаем | Цена |
|---|---|---|
| **B1. Ломаем чисто** | Папки переименовываются, в README и в описании релиза прямым текстом: «перекачайте загрузчик, старые флешки перезапишите» | 0 строк кода, но каждый, кто запустит старый лоадер, увидит тишину |
| **B2. Со shim-файлами** | В старых папках остаётся по одному маленькому `manager.ps1` (~20 строк), который сам подтягивает актуальную версию. Старый лоадер продолжает работать и приводит систему к новой | ~40 строк, страховка от потока «а у меня ничего не произошло» |

Рекомендация: **B2**, потому что старых лоадеров в природе уже сколько-то есть, а цена — полстраницы кода.

### Чего делать НЕ надо

**Не переписывать историю** (force-push, squash «под чистую»). Именно она только что позволила точно ответить, какой файл в какой папке новее и где потерялась июльская правка. «Чистый» репозиторий эту возможность уничтожает — и ровно поэтому был задан вопрос «а какая папка новее». Порядок в проекте даёт тег + CHANGELOG + новая структура, а не стёртая история.

## 9. Что нужно от тебя

1. **Токен GitHub** — когда будешь готов:
   - Settings → Developer settings → Personal access tokens → **Fine-grained tokens**;
   - Repository access: **Only select repositories** → `AgentSharik/WAD`;
   - Permissions: **Contents: Read and write** (+ **Pull requests: Read and write**, если хочешь, чтобы я сам открывал PR);
   - Expiration: **7 дней**.
   Токен будет виден в переписке — после работы отзови его (Revoke) не глядя.
2. **Прогон в VM** по протоколу от меня: снапшот до старта, какие логи и скриншоты забрать. Это твоя часть, и её не делает ни один браузерный ассистент.
3. **Только одно решение по структуре:** подтвердить, что режимы остаются как есть (Clean = 5 задач, Custom = 4), а дублирование файлов убираем. Если хочешь сохранить имена папок — можно оставить их как «профили» без копий содержимого, но тогда оба лоадера надо поправить в один заход, поскольку они ссылаются на пути.
